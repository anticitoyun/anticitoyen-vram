Шлюз інференсу, сумісний з API OpenAI, який розглядає пам'ять як ієрархію і
дає кожному GPU той числовий формат, який його кремній читає найкраще.

Створений для однієї конкретної машини:

| | |
|---|---|
| Процесор | Intel Core i9-14900K (8 P-ядер + 16 E-ядер) |
| Материнська плата | ASUS ROG Maximus Z790 Dark Hero |
| Пам'ять | 96 ГБ DDR5 |
| GPU 0 | ASUS RTX 5090 Astral LC OC, 32 ГБ — Blackwell, `sm_120` |
| GPU 1 | ASUS RTX 3080 Ti, 12 ГБ — Ampere, `sm_86` |
| Система | Ubuntu 26.04 LTS (CUDA 13); обидві карти в PCIe x8/x8, обмежені 400 Вт / 275 Вт |

## Дві ідеї

**Один формат на GPU.** RTX 5090 має тензорні ядра FP4; RTX 3080 Ti їх не
має, як не має і FP8. Звести обидві до спільного формату означало б
змарнувати 5090. Тому конвертер записує *ту саму модель двічі*, у форматі,
який кожне призначення справді вміє використати:

| | RTX 5090 | RTX 3080 Ti |
|---|---|---|
| ваги | **NVFP4** — E2M1 + масштаб FP8 E4M3 на кожні 16 | **INT4** — uint4 + масштаб і нуль fp16 на кожні 128 |
| біт на вагу | 4,50 | 4,16 |
| порівняно з BF16 | у 3,56 раза менший | у 3,85 раза менший |
| режим обчислень | тензорні ядра FP4 | деквантування у FP16 всередині ядра, тензорні ядра FP16 |
| KV-кеш | INT8 | INT8 |

32 ГБ VRAM при 4,5 біта на вагу вміщують близько **56 мільярдів
параметрів** проти 16 мільярдів у BF16. На двох картах це приблизно
**78 мільярдів резидентних параметрів** ще до звернення до оперативної
пам'яті.

**Пам'ять — це ієрархія, а не стіна.** Три рівні, і планувальник вимірює,
скільки коштує кожен, замість сподіватися, що модель поміститься:

```
RTX 5090     32 Go   ~1790 Go/s     NVFP4
RTX 3080 Ti  12 Go    ~912 Go/s     INT4
DDR5 hôte    96 Go   limité par le PCIe ou la DDR
```

## Швидкий старт

```bash
./install.sh                       # environnement virtuel + torch cu128 + acvram
acvram doctor                      # cette machine est-elle prête, et pour quoi
acvram detect                      # qu'y a-t-il réellement ici

acvram plan  ~/modeles/Qwen3-32B                    # où irait chaque couche
acvram convert ~/modeles/Qwen3-32B -o ~/acv/qwen3-32b
acvram serve ~/acv/qwen3-32b --port 8000
```

Потім під'єднується будь-який клієнт OpenAI:

```bash
curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3-32b","messages":[{"role":"user","content":"Bonjour"}],"stream":true}'
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="inutilise")
client.chat.completions.create(model="qwen3-32b",
                               messages=[{"role": "user", "content": "Bonjour"}])
```

## Що каже `acvram plan`

Планувальник варто запустити перед будь-яким завантаженням. Він відповідає
на питання, які вирішують, чи придатна модель для цієї машини:

```
$ acvram plan ~/modeles/Llama-3.3-70B --max-model-len 32768 --max-seqs 4

  etage   format      capacite      poids         KV  tranche
  cuda:0  nvfp4        30,3 Gio   25,5 Gio   4,5 Gio  couches 0-58
  cuda:1  int4_awq     10,9 Gio    8,7 Gio   1,6 Gio  couches 59-79
  cpu     nvfp4        74,8 Gio    3,4 Gio       0 o  -

  poids au total     37,6 Gio
  lu par jeton       35,1 Gio
  KV par jeton       162,5 Kio  -> 39 843 jetons en cache
  MLP en RAM hote    55-58

  decodage estime    17,8 jetons/s  (lot de 1)
  prefill estime     847 jetons/s
```

Він досліджує простір конфігурацій замість того, щоб узяти першу-ліпшу, і
два його рішення достатньо неочевидні, щоб їх проговорити:

* **Він залишає 3080 Ti без роботи**, коли модель поміщається на самій 5090.
  Частини конвеєра виконуються послідовно: додати ступінь на 912 ГБ/с у
  конвеєр на 1790 ГБ/с — значить сповільнити декодування одного потоку.
  Примусово: `--gpus all`.
* **Він стискає KV-кеш, щоб утримати ваги у VRAM.** Кожен гігабайт, відданий
  кешу, — це гігабайт ваг, витіснений на шину PCIe, а читання ваги через PCIe
  коштує приблизно у тридцять разів дорожче, ніж із VRAM. На 70B вище лише
  цей компроміс переводить з 2,3 на 17,8 токена/с.

## Швидше

Чотири оптимізації, кожна перевірена доказом еквівалентності, а не лише
секундоміром: оптимізація, що змінює відповідь, — це помилка.

### Спекулятивне декодування (`--speculative`)

Декодувати один токен з батчем розміру 1 — задача, обмежена пам'яттю:
машина читає всі активні ваги заради одного токена. Перевірка K
запропонованих токенів читає ті самі ваги **один раз**. Два пропонувальники:

* `ngram` (типово) — шукає поточний суфікс раніше в контексті й пропонує те,
  що за ним ішло. Нічого не коштує, не потребує моделі. Окупається, коли
  вивід копіює ввід: правка коду, RAG, резюме.
* `draft` — маленька модель на другому пристрої. На цій збірці це
  RTX 3080 Ti, яку планувальник навмисно лишає вільною для будь-якої моделі,
  що поміщається на 5090.

Прийняття точне, а не наближене: пропозиція приймається з імовірністю
`min(1, p/q)`, а відхилення пересемплює з нормованої додатної частини
`p - q`. За 40 000 розіграшами проти навмисно погано відкаліброваної чернетки
видане розподілення лишається в межах 0,002 повної варіації від цілі —
спекуляція купує швидкість, але ніколи іншу відповідь.

```
modele jouet, glouton, k=4    etapes   jetons/etape   sortie
  sans speculation                23           1,00   reference
  n-grammes                       13           1,77   identique
  brouillon (= cible)              5           4,60   identique
```

### Кеш префіксів (увімкнений типово)

Блоки адресуються *ланцюговим* хешем свого зрізу токенів: два запити зі
спільною системною інструкцією поділяють її блоки, і другому не треба їх
перераховувати. Ланцюжок необхідний: ті самі шістнадцять токенів в іншому
контексті не містять тих самих ключів і значень, а хеш самого лише зрізу
підсунув би кеш однієї послідовності іншій.

Звільнений блок, вміст якого лишається впізнаваним, потрапляє до черги LRU,
а не до списку вільних: так кеш переживає запити, ніколи не відмовляючи у
виділенні, яке міг би обслужити.

### Обчислення на рівні хоста (`--host-exec`)

Шар, ваги якого лежать у RAM, можна скопіювати на GPU або обчислити на місці.
Обидва шляхи обмежені пам'яттю й читають ті самі байти: швидший той, у кого
ширша шина — PCIe 5.0 x16 дає близько 54 ГБ/с, двоканальна DDR5 близько
70 ГБ/с, — а обчислення на місці до того ж лишає GPU вільним, замість
змушувати його чекати копію.

Це окупається, лише якщо процесор читає 4-бітні запаковані ваги напряму.
Звідси маленьке ядро на C++ зі шляхом AVX2 (`acvram_cpu.cpp`, завантажується
через ctypes, без заголовків Python і без ninja). Навіть на своїй
**скалярній** запасній гілці воно випереджає `dequantize() @ x` у 1,44 раза в
INT4 і в 3,21 раза в NVFP4, бо останній спершу пише 32-бітну копію всієї
матриці.

На Mistral-Large-123B оцінка планувальника зростає з 1,35 до 2,42 токена/с.

### Змішана точність (`--snr-floor`, типово вимкнена)

Конвертер вимірює відношення сигнал/шум на виході кожного шару для кожного
тензора й може підвищити до ширшого формату ті, що опускаються нижче
`--snr-floor`, у межах 15 % тензорів і цінової стелі
(`--promotion-cout-max`, у доданих мебібайтах).

Поріг **типово дорівнює нулю**: нічого не підвищується. Декодування
обмежене пропускною здатністю пам'яті, і вимірювання на `Huihui-Qwen3.8-27B`
вирішує — поріг 25 дБ коштує 13,4 % пам'яті та 10,6 % пропускної здатності
(18,50 ГіБ і 41,8 т/с проти 16,02 і 46,2) заради 2,0 % перплексії (42,591
проти 43,447, корпус 16 383 токени). `--snr-floor 25` повертає попередню
поведінку, коли якість важливіша за швидкість.

### І `acvram eval`

Відношення сигнал/шум і косинус логітів — наближення.
`acvram eval КАТ [КАТ ...]` вимірює перплексію ковзним вікном, щоб вибір
формату вирішувався на доказах:

```
$ acvram eval ~/acv/qwen3-32b-nvfp4 ~/acv/qwen3-32b-int4
  modele                   ppl     bpp      taille    jetons
  qwen3-32b-nvfp4        6,412    4,51    17,4 Gio      8192
  qwen3-32b-int4         6,583    4,17    16,1 Gio      8192  (+2,7 %)
```

## Точки входу HTTP

| точка входу | примітки |
|---|---|
| `POST /v1/chat/completions` | потік SSE або єдина відповідь; використовує шаблон діалогу моделі |
| `POST /v1/completions` | промпт текстом або ідентифікаторами токенів |
| `POST /v1/embeddings` | усереднені кінцеві приховані стани, L2-нормовані, `dimensions` враховується |
| `GET /v1/models` | плюс блок `acvram`: формати, пристрої, ємність KV-кешу |
| `GET /health`, `GET /metrics` | швидкість декодування, зайнятість блоків KV |

Назви полів цих відповідей лишаються англійськими: це протокол OpenAI, і
їхній переклад зламав би всіх наявних клієнтів.

## Звідки взяті числа

Кожне значення вище отримане кодом цього репозиторію й перевірене `pytest`.
Вимірювання на процесорі з еталонними ядрами:

| формат | біт/вагу | SNR ваг | косинус логітів vs BF16 |
|---|---|---|---|
| BF16 | 16,00 | — | 1,0000 |
| INT8 | 8,19 | 44,6 дБ | 0,9998 |
| NVFP4 | 4,50 | 20,4 дБ | 0,9664 |
| INT4 | 4,16 | 20,0 дБ | 0,9427 |
| INT4 + Hadamard | 4,16 | 21,0 дБ | 0,9582 |

Два висновки з цих вимірювань змінили типові значення:

* **Поворот Адамара допомагає INT4, але не NVFP4.** Групи по 128 в INT4 не
  можуть поглинути поодинокий викидний канал, тож розмазати крайні значення
  варте перетворення n log n на активацію. Блоки по 16 у NVFP4 уже несуть
  власний масштаб. Звідси `--hadamard auto`, що застосовує його лише до INT4.
* **INT8 випереджає FP8 E4M3 для KV-кешу**: 44 дБ проти 32 дБ за однакового
  розміру, бо масштаб на (токен, голову) вже дає той динамічний діапазон, на
  який FP8 витрачає біти експоненти. Тому обидві карти використовують KV-кеш
  в INT8, хоча 5090 уміє FP8.

## Виміряні результати (22.09.2026, RTX 5090 при 400 Вт, режим ≥ 20 с за лічильником енергії)

Qwen3-Coder-30B-A3B у NVFP4 (експерти) + INT8 (увага, голова), один
протокол для всіх рушіїв (`outils/`, одна карта, `energie.py`):

| | acvram 0.6.35 | vLLM 0.29 (CUTLASS FP4) | llama.cpp (sm_120) |
|---|---|---|---|
| декодування, 12 послідовностей | **1 625,5 т/с** | 1 596,1 т/с | — |
| декодування, 1 послідовність | **380,8 т/с** | 290,6 т/с | 323,6 т/с |
| prefill pp2048 | **22 707** токенів/с | 21 054 | 8 671 (TabbyAPI, відкликано) |

Пропускна здатність на сьогодні (стенд 1030, еко-режим `-lgc 2700`, конвеєр у роботі; жадібна вибірка захоплена в графі CUDA, за замовчуванням з 0.6.35). b=12 — офіційна запечатана комірка (медіана 6 чергованих вікон, частота по вікну). Значення vLLM 1 596,1 — заморожений еталон від 21.09 (vLLM того дня не перезапускався): розрив +1,84 % чинний за рівного еталона, а не як перевимірювання обох одного ранку. Дж/токен за рівної частоти проти трьох рушіїв досі перевимірюється (`outils/gpu/mesure/banc-4moteurs.py`) — число без режиму не публікується.

Уранці 14.09 acvram показував у тій самій комірці 630 т/с і 0,619 Дж/токен:
виграш дали нативний FP4 MMA Blackwell (`mma.sync … kind::mxf4nvf4`, ×7,9
до bf16), MoE як згрупований GEMM за кошиком батча, маршрутизація одним
ядром (3 677 → 1 517 запусків за крок) і вузький GEMM на тензорних ядрах для
проєкцій. Кожне число має нотатку в `acvram-memoire/revue/` з прогнозом,
запечатаним до вимірювання, інструментом і його режимом — число без режиму
не публікується.

Де acvram попереду: моделі MLA (GLM-4.7-Flash) у нативному NVFP4 sm_120
(b=1: 165,35 т/с у роботі), які vLLM обслуговує лише в FP8; моделі, що не
вміщаються у VRAM; і, починаючи з 0.6.35, декодування великим батчем MoE, що
вміщається у VRAM — b=12 зріс з 1 540 (0.6.34) до 1 625,5 т/с, тобто +1,84 %
попереду замороженого еталона vLLM (1 596,1). Розрив лишається вузьким і за
замороженого еталона; розрив за енергією ще належить перевиміряти.

## Стан

Версія 0.6.35. Усе працює на 5090: ядра CUDA, зібрані для `sm_120a`
(нативний FP4) і `sm_86`, графи CUDA, квантування NVFP4/INT8/INT4,
HTTP-сервер. Огорожі на місці: карта невидима для робочих сесій
(`CUDA_VISIBLE_DEVICES` порожній), і лише `outils/carte.sh` видає її під
блокуванням одному вимірюванню за раз; сторож журналює будь-який доступ поза
блокуванням; вимірювання енергії, що охоплює більше однієї карти або менше
10 с, визнається недійсним; модель, завантажена в деградованому режимі,
повідомляє про це й не бере участі в дуелі.

640 тестів (`pytest -q`, хвилина на процесорі; GPU-тести виконуються лише
під `carte.sh`). Облік роботи: `acvram-memoire/` (правила, довідник,
зошити, рев'ю зі 180 нотаток).
