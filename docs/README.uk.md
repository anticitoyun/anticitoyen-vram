## Дві ідеї

Розроблено під конкретну машину:

| | |
|---|---|
| Процесор | Intel Core i9-14900K (8 ядер P + 16 ядер E) |
| Материнська плата | ASUS ROG Maximus Z790 Dark Hero |
| Пам'ять | 96 Go DDR5 |
| GPU 0 | ASUS RTX 5090 Astral LC OC, 32 Go — Blackwell, `sm_120` |
| GPU 1 | ASUS RTX 3080 Ti, 12 Go — Ampere, `sm_86` |
| Система | Ubuntu 26.04 LTS (CUDA 13); обидві карти в PCIe x8/x8, обмежені 400 Вт / 275 Вт |

**Свій формат для кожного GPU.** RTX 5090 має тензорні ядра FP4; RTX 3080 Ti їх не має, як і FP8. Приведення обох до спільного формату марно витратило б можливості 5090. Тому конвертер записує *ту саму модель двічі*, у форматі, який кожен отримувач справді здатен використати:

| | RTX 5090 | RTX 3080 Ti |
|---|---|---|
| ваги | **NVFP4** — E2M1 + масштаб FP8 E4M3 на кожні 16 | **INT4** — uint4 + масштаб і нуль fp16 на кожні 128 |
| бітів на вагу | 4,50 | 4,16 |
| проти BF16 | у ×3,56 менше | у ×3,85 менше |
| режим обчислення | тензорні ядра FP4 | деквантизація у FP16 всередині ядра, тензорні ядра FP16 |
| кеш KV | INT8 | INT8 |

32 Go VRAM за 4,5 біта на вагу вміщують приблизно **56 мільярдів параметрів**, проти 16 мільярдів у BF16. На обох картах разом це дає близько **78 мільярдів резидентних параметрів** ще до звернення до оперативної пам'яті.

**Пам'ять — це ієрархія, а не стіна.** Три рівні, і планувальник вимірює вартість кожного, замість того щоб сподіватися, що модель поміститься:

```
RTX 5090     32 Go   ~1790 Go/s     NVFP4
RTX 3080 Ti  12 Go    ~912 Go/s     INT4
DDR5 hôte    96 Go   limité par le PCIe ou la DDR
```

## Швидкий старт

```bash
./install.sh                       # віртуальне середовище + torch cu128 + acvram
acvram doctor                      # чи готова ця машина, і до чого
acvram detect                      # що тут насправді є

acvram plan  ~/modeles/Qwen3-32B                    # куди піде кожен шар
acvram convert ~/modeles/Qwen3-32B -o ~/acv/qwen3-32b
acvram serve ~/acv/qwen3-32b --port 8000
```

Будь-який клієнт OpenAI підключається потім так:

```bash
curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3-32b","messages":[{"role":"user","content":"Привіт"}],"stream":true}'
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="inutilise")
client.chat.completions.create(model="qwen3-32b",
                               messages=[{"role": "user", "content": "Привіт"}])
```

## Встановлення

З вихідного коду (будь-яка платформа):

```bash
git clone https://github.com/anticitoyun/anticitoyen-vram.git && cd anticitoyen-vram
./install.sh
```

Або пакетом, файл прикріплений до кожного [релізу на GitHub](https://github.com/anticitoyun/anticitoyen-vram/releases/latest):

| Канал | Файл, прикріплений до релізу | Команда |
|---|---|---|
| Debian / Ubuntu (.deb) | `acvram_<version>_amd64.deb` | `sudo dpkg -i acvram_<version>_amd64.deb` |
| Arch (AUR) | `aur-<version>.tar.gz` (PKGBUILD + .SRCINFO) | `tar xzf aur-<version>.tar.gz && cd acvram && makepkg -si` |
| Fedora / COPR (RPM) | `.rpm` / `.src.rpm` (імена, згенеровані `rpmbuild`, не фіксовані) | `sudo rpm -i acvram-<version>-1.*.noarch.rpm` (або `rpmbuild --rebuild *.src.rpm` з `.src.rpm`) |
| Flatpak | `acvram-<version>.flatpak` | `flatpak install acvram-<version>.flatpak` |

Pip не публікується як пакет (немає зібраного wheel): `pip install -e '.[dev]'` встановлює з клону вихідного коду, так само як `./install.sh`.

<a id="plan"></a>

## Що показує `acvram plan`

Планувальник варто запускати перед будь-яким завантаженням. Він відповідає на питання, що вирішують, чи придатна модель для цієї машини:

```
$ acvram plan ~/modeles/Llama-3.3-70B --max-model-len 32768 --max-seqs 4

  etage   format      capacite      poids         KV  tranche
  cuda:0  nvfp4        30,3 Gio   25,5 Gio   4,5 Gio  couches 0-58
  cuda:1  int4_awq     10,9 Gio    8,7 Gio   1,6 Gio  couches 59-79
  cpu     nvfp4        74,8 Gio    3,4 Gio       0 o  -

  poids au total     37,6 Gio
  lu par jeton       35,1 Gio
  KV par jeton       162,5 Kio  -> 39 843 jetons en cache
  MLP en RAM hote    55-58

  decodage estime    17,8 jetons/s  (lot de 1)
  prefill estime     847 jetons/s
```

Він досліджує простір конфігурацій, а не зупиняється на першій придатній, і два його рішення достатньо контрінтуїтивні, щоб їх варто було пояснити:

* **Він залишає 3080 Ti невикористаною**, коли модель уміщується лише на 5090. Ланки конвеєра виконуються послідовно: додавання етапу на 912 Go/s у конвеєр на 1790 Go/s сповільнює декодування при єдиному потоці. Примусово вмикається прапорцем `--gpus all`.
* **Він звужує кеш KV, щоб утримати ваги в VRAM.** Кожен гібібайт, відданий кешу, — це гібібайт ваг, витіснений на шину PCIe, а читання ваги через PCIe коштує приблизно у тридцять разів дорожче, ніж з VRAM. На 70B вище саме цей вибір піднімає швидкість із 2,3 до 17,8 токенів/с.

<a id="optimisations"></a>

## Пришвидшення роботи

Чотири оптимізації, кожна перевірена доказом еквівалентності, а не лише секундоміром: оптимізація, що змінює відповідь, — це баг.

Лінійні шари NVFP4 щільних моделей за умовчанням проходять через розкладку Marlin (+57–90 % пропускної здатності при b = 8, TTFT +2–4 мс за revue/poste6-piece147-verdict-24-09.md; відкат через `ACVRAM_PROJ_MARLIN=0`, див. [CHANGELOG.md](../CHANGELOG.md)).

### Спекулятивне декодування (`--speculative`)

Декодування одного токена з розміром пакета 1 обмежене пропускною здатністю пам'яті: машина зчитує всі активні ваги, щоб виробити лише один токен. Перевірка K запропонованих токенів зчитує ті самі ваги **лише один раз**. Два механізми пропозиції:

* `ngram` (за умовчанням) — шукає поточний суфікс раніше в контексті і пропонує те, що за ним ішло. Нічого не коштує, не потребує жодної моделі. Вигідний, коли вихід повторює вхід: редагування коду, RAG, реферування.
* `draft` — невелика модель на другому пристрої. На цьому стенді таким пристроєм є RTX 3080 Ti, яку планувальник навмисно залишає простоювати для будь-якої моделі, що уміщується на 5090.

`mtp` (голова `nextn` моделі) і `auto` також існують; наразі невигідні й не увімкнені за умовчанням — див. `docs/ARCHITECTURE.md`.

Прийняття точне, а не наближене: пропозиція приймається з імовірністю `min(1, p/q)`, а при відмові виконується повторна вибірка з нормалізованої додатної частини `p - q`. При вимірюванні на 40 000 вибірках проти навмисно погано відкаліброваного чернетки підсумковий розподіл лишається в межах 0,002 повної варіації від цілі — спекуляція купує швидкість, але ніколи не іншу відповідь.

```
modele jouet, glouton, k=4    etapes   jetons/etape   sortie
  sans speculation                23           1,00   reference
  n-grammes                       13           1,77   identique
  brouillon (= cible)              5           4,60   identique
```

### Кеш префіксів (увімкнено за умовчанням)

Блоки адресуються *ланцюговим* хешем свого фрагмента токенів: два запити, що поділяють системну інструкцію, поділяють її блоки, і другому більше не потрібно їх переобчислювати. Ланцюг необхідний: ті самі шістнадцять токенів в іншому контексті не містять тих самих ключів і значень, і хешування лише фрагмента обслуговувало б кеш однієї послідовності на користь іншої.

Звільнений блок, вміст якого лишається впізнаваним, потрапляє в чергу LRU, а не в список вільних блоків: так кеш переживає між запитами, ніколи не відмовляючи у виділенні, яке міг би обслужити.

### Обчислення на стороні хоста (`--host-exec`)

Шар, чиї ваги розміщені в оперативній пам'яті, можна скопіювати на GPU або обчислити на місці. Обидва шляхи обмежені пропускною здатністю пам'яті й читають ті самі байти: швидший той, у кого ширша шина — PCIe 5.0 x16 дає близько 54 Go/s, DDR5 у дворежимному каналі близько 70 Go/s, — а обчислення на місці до того ж звільняє GPU замість того, щоб змушувати його чекати на копію.

Це виправдано лише тоді, коли процесор читає безпосередньо ваги, упаковані в 4 біти. Звідси невелике ядро на C++ зі шляхом AVX2 (`acvram_cpu.cpp`, завантажуване через ctypes, без заголовків Python і без ninja). Навіть на своїй **скалярній** резервній гілці воно випереджає `dequantize() @ x` у 1,44 раза на INT4 і в 3,21 раза на NVFP4, бо останній спочатку записує 32-бітну копію всієї матриці.

На Mistral-Large-123B оцінка планувальника піднімається з 1,35 до 2,42 токенів/с.

### Змішана точність (`--snr-floor`, за умовчанням вимкнена)

Конвертер вимірює співвідношення сигнал/шум на виході кожного шару для кожного тензора і може підвищувати формат тим, хто опускається нижче `--snr-floor`, у межах 15 % тензорів і граничної ціни (`--promotion-cout-max`, у доданих мебібайтах).

Поріг **дорівнює нулю за умовчанням**: нічого не підвищується. Декодування обмежене пропускною здатністю пам'яті, і вимірювання на `Huihui-Qwen3.8-27B` дає відповідь — поріг у 25 dB коштує 13,4 % пам'яті й 10,6 % пропускної здатності (18,50 Gio і 41,8 t/s проти 16,02 і 46,2) заради 2,0 % перплексії (42,591 проти 43,447, корпус із 16 383 токенів). `--snr-floor 25` відновлює попередню поведінку, коли якість важливіша за швидкість.

### І `acvram eval`

Співвідношення сигнал/шум і косинус логітів — лише наближення. `acvram eval REP [REP ...]` вимірює перплексію ковзним вікном, щоб вибір формату вирішувався доказами:

```
$ acvram eval ~/acv/qwen3-32b-nvfp4 ~/acv/qwen3-32b-int4
  modele                   ppl     bpp      taille    jetons
  qwen3-32b-nvfp4        6,412    4,51    17,4 Gio      8192
  qwen3-32b-int4         6,583    4,17    16,1 Gio      8192  (+2,7 %)
```

## Точки входу HTTP

| точка входу | примітки |
|---|---|
| `POST /v1/chat/completions` | потік SSE або єдина відповідь; використовує шаблон діалогу моделі |
| `POST /v1/completions` | підказка у вигляді тексту або ідентифікаторів токенів |
| `POST /v1/embeddings` | усереднені фінальні приховані стани, нормовані за L2, `dimensions` дотримується |
| `GET /v1/models` | плюс блок `acvram`: формати, пристрої, ємність кешу KV |
| `GET /health`, `GET /metrics` | швидкість декодування, зайнятість блоків KV |

Назви полів цих відповідей лишаються англійською: це протокол OpenAI, і їхній переклад зламав би всіх наявних клієнтів.

<a id="chiffres"></a>

## Звідки беруться цифри

Кожне наведене вище значення отримане кодом цього репозиторію та перевірене через `pytest`. Вимірювання виконані на процесорі з еталонними ядрами:

| формат | бітів/вага | SNR ваг | косинус логітів проти BF16 |
|---|---|---|---|
| BF16 | 16,00 | — | 1,0000 |
| INT8 | 8,19 | 44,6 dB | 0,9998 |
| NVFP4 | 4,50 | 20,4 dB | 0,9664 |
| INT4 | 4,16 | 20,0 dB | 0,9427 |
| INT4 + Hadamard | 4,16 | 21,0 dB | 0,9582 |

Два спостереження з цих вимірювань змінили значення за умовчанням:

* **Обертання Адамара допомагає INT4, але не NVFP4.** Групи по 128 в INT4 не можуть поглинути одиничний викид каналу, тож розподіл екстремальних значень вартий перетворення порядку n log n на активацію. Блоки по 16 в NVFP4 вже несуть власний масштаб. Звідси `--hadamard auto`, що застосовує його лише до INT4.
* **INT8 перевершує FP8 E4M3 для кешу KV** — 44 dB проти 32 dB за однакового розміру, бо масштаб на пару (токен, голова) вже дає той динамічний діапазон, на який FP8 витрачає біти експоненти. Обидві карти тому використовують кеш KV в INT8, навіть якщо 5090 могла б працювати у FP8. Формат `k8v4` (значення в INT4, −22 % байтів кешу) існує як опція, **некваліфікована** — див. `docs/ARCHITECTURE.md`.

<a id="etat"></a>

## Стан

Версія 0.6.38. Все працює на 5090: ядра CUDA скомпільовані для `sm_120a` (нативний FP4) і `sm_86`, графи CUDA, квантування NVFP4/INT8/INT4, HTTP-сервер. Запобіжники на місці: карта невидима робочим сесіям (`CUDA_VISIBLE_DEVICES` порожній), і лише `outils/carte.sh` надає її, під блокуванням, для одного вимірювання за раз; спостерігач журналює будь-який доступ поза блокуванням; вимірювання енергії, що охоплює більш ніж одну карту або менш ніж 10 с, відкидається; модель, завантажена в деградованому режимі, оголошує це і не бере участі в дуелі.

4 107 тестів (`pytest --collect-only -q`, одна хвилина на процесорі; тести GPU виконуються лише під `carte.sh`). Облік роботи: `acvram-memoire/` (правила, довідник, щоденники, огляд кількох сотень нотаток).
