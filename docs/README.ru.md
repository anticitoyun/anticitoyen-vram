## Две идеи

Разработано под конкретную машину:

| | |
|---|---|
| Процессор | Intel Core i9-14900K (8 P-ядер + 16 E-ядер) |
| Материнская плата | ASUS ROG Maximus Z790 Dark Hero |
| Память | 96 Go DDR5 |
| GPU 0 | ASUS RTX 5090 Astral LC OC, 32 Go — Blackwell, `sm_120` |
| GPU 1 | ASUS RTX 3080 Ti, 12 Go — Ampere, `sm_86` |
| Система | Ubuntu 26.04 LTS (CUDA 13); обе карты в PCIe x8/x8, ограничены 400 Вт / 275 Вт |

**Свой формат на каждый GPU.** У RTX 5090 есть тензорные ядра FP4; у RTX 3080 Ti их нет, как и FP8. Приведение обеих карт к общему формату впустую растратило бы возможности 5090. Поэтому конвертер записывает *одну и ту же модель дважды*, в том формате, который каждый получатель реально способен использовать:

| | RTX 5090 | RTX 3080 Ti |
|---|---|---|
| веса | **NVFP4** — E2M1 + масштаб FP8 E4M3 на каждые 16 | **INT4** — uint4 + масштаб и ноль fp16 на каждые 128 |
| бит на вес | 4,50 | 4,16 |
| против BF16 | в ×3,56 меньше | в ×3,85 меньше |
| режим вычисления | тензорные ядра FP4 | деквантизация в FP16 внутри ядра, тензорные ядра FP16 |
| кэш KV | INT8 | INT8 |

32 Go VRAM при 4,5 бита на вес вмещают примерно **56 миллиардов параметров**, против 16 миллиардов в BF16. На обеих картах вместе это даёт около **78 миллиардов резидентных параметров** ещё до обращения к оперативной памяти.

**Память — иерархия, а не стена.** Три уровня, и планировщик измеряет стоимость каждого, вместо того чтобы надеяться, что модель поместится:

```
RTX 5090     32 Go   ~1790 Go/s     NVFP4
RTX 3080 Ti  12 Go    ~912 Go/s     INT4
DDR5 hôte    96 Go   limité par le PCIe ou la DDR
```

## Быстрый старт

```bash
./install.sh                       # виртуальное окружение + torch cu128 + acvram
acvram doctor                      # готова ли эта машина, и к чему
acvram detect                      # что здесь есть на самом деле

acvram plan  ~/modeles/Qwen3-32B                    # куда пойдёт каждый слой
acvram convert ~/modeles/Qwen3-32B -o ~/acv/qwen3-32b
acvram serve ~/acv/qwen3-32b --port 8000
```

Любой клиент OpenAI подключается затем так:

```bash
curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3-32b","messages":[{"role":"user","content":"Привет"}],"stream":true}'
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="inutilise")
client.chat.completions.create(model="qwen3-32b",
                               messages=[{"role": "user", "content": "Привет"}])
```

## Установка

Из исходного кода (любая платформа):

```bash
git clone https://github.com/anticitoyun/anticitoyen-vram.git && cd anticitoyen-vram
./install.sh
```

Или пакетом, файл прикреплён к каждому [релизу на GitHub](https://github.com/anticitoyun/anticitoyen-vram/releases/latest):

| Канал | Файл, прикреплённый к релизу | Команда |
|---|---|---|
| Debian / Ubuntu (.deb) | `acvram_<version>_amd64.deb` | `sudo dpkg -i acvram_<version>_amd64.deb` |
| Arch (AUR) | `aur-<version>.tar.gz` (PKGBUILD + .SRCINFO) | `tar xzf aur-<version>.tar.gz && cd acvram && makepkg -si` |
| Fedora / COPR (RPM) | `.rpm` / `.src.rpm` (имена, генерируемые `rpmbuild`, не фиксированы) | `sudo rpm -i acvram-<version>-1.*.noarch.rpm` (или `rpmbuild --rebuild *.src.rpm` из `.src.rpm`) |
| Flatpak | `acvram-<version>.flatpak` | `flatpak install acvram-<version>.flatpak` |

Pip не публикуется как пакет (нет собранного wheel): `pip install -e '.[dev]'` устанавливает из клона исходников, так же как `./install.sh`.

<a id="plan"></a>

## Что показывает `acvram plan`

Планировщик стоит запускать перед любой загрузкой. Он отвечает на вопросы, которые решают, пригодна ли модель для этой машины:

```
$ acvram plan ~/modeles/Llama-3.3-70B --max-model-len 32768 --max-seqs 4

  etage   format      capacite      poids         KV  tranche
  cuda:0  nvfp4        30,3 Gio   25,5 Gio   4,5 Gio  couches 0-58
  cuda:1  int4_awq     10,9 Gio    8,7 Gio   1,6 Gio  couches 59-79
  cpu     nvfp4        74,8 Gio    3,4 Gio       0 o  -

  poids au total     37,6 Gio
  lu par jeton       35,1 Gio
  KV par jeton       162,5 Kio  -> 39 843 jetons en cache
  MLP en RAM hote    55-58

  decodage estime    17,8 jetons/s  (lot de 1)
  prefill estime     847 jetons/s
```

Он исследует пространство конфигураций, а не останавливается на первой подходящей, и два его решения достаточно контринтуитивны, чтобы их стоило пояснить:

* **Он оставляет 3080 Ti неиспользованной**, если модель помещается на одну лишь 5090. Ступени конвейера выполняются последовательно: добавление этапа на 912 Go/s в конвейер на 1790 Go/s замедляет декодирование при единственном потоке. Принудительно включается флагом `--gpus all`.
* **Он сокращает кэш KV, чтобы удержать веса в VRAM.** Каждый гибибайт, отданный кэшу, — это гибибайт весов, вытесненный на шину PCIe, а чтение веса через PCIe стоит примерно в тридцать раз дороже, чем из VRAM. На 70B выше именно этот выбор поднимает скорость с 2,3 до 17,8 токенов/с.

<a id="optimisations"></a>

## Ускорение работы

Четыре оптимизации, каждая проверена доказательством эквивалентности, а не только секундомером: оптимизация, меняющая ответ, — это баг.

Линейные слои NVFP4 плотных моделей по умолчанию проходят через раскладку Marlin (+57–90 % пропускной способности при b = 8, TTFT +2–4 мс согласно revue/poste6-piece147-verdict-24-09.md; откат через `ACVRAM_PROJ_MARLIN=0`, см. [CHANGELOG.md](../CHANGELOG.md)).

### Спекулятивное декодирование (`--speculative`)

Декодирование одного токена при размере пакета 1 ограничено пропускной способностью памяти: машина считывает все активные веса, чтобы произвести всего один токен. Проверка K предложенных токенов считывает эти же веса **всего один раз**. Два предлагающих механизма:

* `ngram` (по умолчанию) — ищет текущий суффикс раньше в контексте и предлагает то, что за ним следовало. Ничего не стоит, не требует модели. Выгоден, когда выход повторяет вход: правка кода, RAG, резюмирование.
* `draft` — небольшая модель на втором устройстве. На этом стенде таким устройством выступает RTX 3080 Ti, которую планировщик намеренно оставляет простаивающей для любой модели, помещающейся на 5090.

`mtp` (голова `nextn` модели) и `auto` тоже существуют; в текущем виде невыгодны и не включены по умолчанию — см. `docs/ARCHITECTURE.md`.

Принятие точное, а не приближённое: предложение принимается с вероятностью `min(1, p/q)`, а при отказе выполняется повторная выборка из нормализованной положительной части `p - q`. При измерении на 40 000 выборках против намеренно плохо откалиброванного черновика итоговое распределение остаётся в пределах 0,002 полной вариации от цели — спекуляция покупает скорость, но никогда не другой ответ.

```
modele jouet, glouton, k=4    etapes   jetons/etape   sortie
  sans speculation                23           1,00   reference
  n-grammes                       13           1,77   identique
  brouillon (= cible)              5           4,60   identique
```

### Кэш префиксов (включён по умолчанию)

Блоки адресуются *цепочечным* хэшем их фрагмента токенов: два запроса, разделяющих системную инструкцию, разделяют её блоки, и второму больше не нужно их пересчитывать. Цепочка необходима: одни и те же шестнадцать токенов в другом контексте не содержат тех же ключей и значений, и хэширование одного лишь фрагмента обслуживало бы кэш одной последовательности в пользу другой.

Освобождённый блок, содержимое которого остаётся опознаваемым, попадает в очередь LRU, а не в список свободных блоков: так кэш переживает между запросами, никогда не отказывая в выделении, которое мог бы обслужить.

### Вычисление на стороне хоста (`--host-exec`)

Слой, чьи веса находятся в оперативной памяти, можно скопировать на GPU или вычислить на месте. Оба пути ограничены пропускной способностью памяти и читают одни и те же байты: быстрее тот, у кого шире шина — PCIe 5.0 x16 даёт около 54 Go/s, DDR5 в двухканальном режиме около 70 Go/s, — а вычисление на месте к тому же освобождает GPU вместо того, чтобы заставлять его ждать копирование.

Это оправдано лишь тогда, когда процессор читает напрямую веса, упакованные в 4 бита. Отсюда небольшое ядро на C++ с путём AVX2 (`acvram_cpu.cpp`, загружаемое через ctypes, без заголовков Python и без ninja). Даже на своей **скалярной** резервной ветке оно обгоняет `dequantize() @ x` в 1,44 раза на INT4 и в 3,21 раза на NVFP4, потому что последний сначала пишет 32-битную копию всей матрицы.

На Mistral-Large-123B оценка планировщика поднимается с 1,35 до 2,42 токенов/с.

### Смешанная точность (`--snr-floor`, по умолчанию выключена)

Конвертер измеряет отношение сигнал/шум на выходе каждого слоя для каждого тензора и может повышать формат тем, кто опускается ниже `--snr-floor`, в пределах 15 % тензоров и предельной цены (`--promotion-cout-max`, в добавленных мебибайтах).

Порог **равен нулю по умолчанию**: ничего не повышается. Декодирование ограничено пропускной способностью памяти, и измерение на `Huihui-Qwen3.8-27B` расставляет точки — порог в 25 dB стоит 13,4 % памяти и 10,6 % пропускной способности (18,50 Gio и 41,8 t/s против 16,02 и 46,2) ради 2,0 % перплексии (42,591 против 43,447, корпус в 16 383 токена). `--snr-floor 25` восстанавливает прежнее поведение, когда качество важнее скорости.

### И `acvram eval`

Отношение сигнал/шум и косинус логитов — лишь приближения. `acvram eval REP [REP ...]` измеряет перплексию скользящим окном, чтобы выбор формата решался доказательствами:

```
$ acvram eval ~/acv/qwen3-32b-nvfp4 ~/acv/qwen3-32b-int4
  modele                   ppl     bpp      taille    jetons
  qwen3-32b-nvfp4        6,412    4,51    17,4 Gio      8192
  qwen3-32b-int4         6,583    4,17    16,1 Gio      8192  (+2,7 %)
```

## Точки входа HTTP

| точка входа | примечания |
|---|---|
| `POST /v1/chat/completions` | поток SSE или единый ответ; использует шаблон диалога модели |
| `POST /v1/completions` | подсказка в виде текста или идентификаторов токенов |
| `POST /v1/embeddings` | усреднённые финальные скрытые состояния, нормированы по L2, `dimensions` соблюдается |
| `GET /v1/models` | плюс блок `acvram`: форматы, устройства, ёмкость кэша KV |
| `GET /health`, `GET /metrics` | скорость декодирования, занятость блоков KV |

Названия полей этих ответов остаются на английском: это протокол OpenAI, и их перевод сломал бы всех существующих клиентов.

<a id="chiffres"></a>

## Откуда взяты цифры

Каждое приведённое выше значение получено кодом этого репозитория и проверено через `pytest`. Измерения проведены на процессоре с эталонными ядрами:

| формат | бит/вес | SNR весов | косинус логитов против BF16 |
|---|---|---|---|
| BF16 | 16,00 | — | 1,0000 |
| INT8 | 8,19 | 44,6 dB | 0,9998 |
| NVFP4 | 4,50 | 20,4 dB | 0,9664 |
| INT4 | 4,16 | 20,0 dB | 0,9427 |
| INT4 + Hadamard | 4,16 | 21,0 dB | 0,9582 |

Два наблюдения из этих измерений изменили значения по умолчанию:

* **Вращение Адамара помогает INT4, но не NVFP4.** Группы по 128 у INT4 не могут поглотить единичный выброс канала, поэтому распределение экстремальных значений стоит преобразования порядка n log n на активацию. Блоки по 16 у NVFP4 уже несут собственный масштаб. Отсюда `--hadamard auto`, применяющий его только к INT4.
* **INT8 превосходит FP8 E4M3 для кэша KV** — 44 dB против 32 dB при одинаковом размере, потому что масштаб на пару (токен, голова) уже даёт тот динамический диапазон, на который FP8 тратит биты экспоненты. Обе карты поэтому используют кэш KV в INT8, даже если 5090 могла бы работать в FP8. Формат `k8v4` (значения в INT4, −22 % байт кэша) существует как опция, **неквалифицированная** — см. `docs/ARCHITECTURE.md`.

Qwen3-Coder-30B-A3B в NVFP4 (эксперты) + INT8 (внимание, голова), единый протокол для всех движков (`outils/`, одна карта, `energie.py`):

| | acvram | vLLM 0.29 (`vllm serve`) | llama.cpp (sm_120) |
|---|---|---|---|
| декодирование, 12 последовательностей | 1 995,1 t/s ² | 2 027,0 t/s ² | — |
| декодирование, 1 последовательность | 312,3 t/s ³ ⁴ | 284,8 t/s ³ | **329,9 t/s** ⁴ |
| prefill pp2048 | **22 707 токенов/с** | 21 054 | 8 671 (TabbyAPI, снят) |

¹ Erratum от 22.09: `serve` по умолчанию спекулирует (`--speculative ngram`, cli.py), конкуренты — нет; опубликованные ранее 380,8 t/s были измерены С СПЕКУЛЯЦИЕЙ. Без спекуляции (`--speculative none`, та же цепочка, revue/poste2-piece44-speculation-none-22-09.md): 283,6 t/s — acvram оказывается **третьим** при b=1, позади llama.cpp и vLLM. По энергии он остаётся впереди llama.cpp (0,601 против 0,700 J/токен нетто). При b=12 спекуляция никогда не активна (защита `lot_max=2`): эта ячейка уже была в равных условиях.

² 23.09, та же сессия, тот же HTTP-клиент (`banc-llamacpp-16-09.py` против `acvram serve` и `vllm serve`), `-lgc 2700` явно выставлен вокруг каждого плеча, чередующиеся ячейки A V V A, ≥ 5 партий на плечо, отклонение объявляется только за пределами 2 σ (revue/poste2-piece96-vllm-b12-rejeu-89-23-09.md). acvram 0.6.38 (w13 при декодировании, развёрнутое сокращение внимания): отклонение −1,6 %, **ниже 2 σ: равенство пропускной способности**. По J/токен **vLLM остаётся впереди на 7,0 %** (за пределами 2 σ). С 0.6.37 тот же протокол давал −4,7 %.

³ Та же сессия и тот же протокол, что и в ², без спекуляции с обеих сторон: acvram 312,3 против vLLM 284,8 — **acvram впереди на 9,7 % по пропускной способности** (за пределами 2 σ); J/токен: **равенство** (отклонение 0,04 %, ниже 2 σ).

⁴ 23.09, тот же протокол против llama.cpp (revue/poste2-piece72-llamacpp-b1-23-09.md), acvram 0.6.37 с переписанной маршрутизацией (+5,6 %): acvram 310,8 против llama.cpp 329,9 t/s — **llama.cpp впереди на 5,8 % по пропускной способности, acvram впереди на 13,4 % по J/токен** (0,598 против 0,691).

Пропускная способность дня (пост 1030, экономичный режим `-lgc 2700`, конвейер в эксплуатации; жадная выборка захвачена в графе CUDA, значение по умолчанию 0.6.35). b=12 у acvram — официальная опечатанная ячейка (медиана 6 чередующихся окон, тактовая частота по окну).

> **Erratum (23.09.2026).** Сравнение с vLLM, публиковавшееся до этого (b=12: 1 782 против 1 634 t/s; b=1: 290,6), сопоставляло acvram, измеренный по HTTP, с vLLM, измеренным **офлайн** (`LLM().generate()`), а erratum от 22.09 ошибочно утверждал, что ячейка vLLM проходит через `vllm serve`. 23.09: единый HTTP-клиент для обоих, и `-lgc` выставлен для обоих (acvram выставляет свой при запуске, `vllm serve` — нет: без этой предосторожности vLLM работал на ~2 930 МГц против ~2 650). Результат в примечании ²: vLLM впереди на 9,1 % при b=12.

Утром 14.09 acvram показывал 630 t/s и 0,619 J/токен на той же ячейке: прирост получен за счёт нативного MMA FP4 архитектуры Blackwell (`mma.sync … kind::mxf4nvf4`, в ×7,9 быстрее bf16), группового GEMM для MoE по корзинам пакета, маршрутизации в едином ядре (3 677 → 1 517 запусков за шаг) и узкого GEMM на тензорных ядрах для проекций. У каждой цифры есть своя запись в `acvram-memoire/revue/` с опечатанным прогнозом до измерения, инструментом и режимом — цифра без режима не публикуется.

Где acvram впереди: модели MLA (GLM-4.7-Flash) в нативном NVFP4 sm_120, которые vLLM обслуживает только в FP8 (b=1: 165,35 t/s в эксплуатации); модели, не помещающиеся в VRAM. Декодирование одной последовательности сюда не относится: без спекуляции acvram там впереди vLLM на 9,7 % (примечание ³), позади llama.cpp на 5,8 % по пропускной способности, но впереди него на 13,4 % по энергии (примечание ⁴). При большом пакете, на MoE, помещающемся в VRAM, vLLM держит равенство пропускной способности при b=12 (1 995,1 против 2 027,0 t/s, ниже 2 σ, примечание ²), но сохраняет на 7,0 % меньше J/токен; acvram здесь прошёл путь от 1 540 t/s (0.6.34) до 1 995 (0.6.38).

<a id="etat"></a>

## Состояние

Версия 0.6.38. Всё работает на 5090: ядра CUDA скомпилированы для `sm_120a` (нативный FP4) и `sm_86`, графы CUDA, квантование NVFP4/INT8/INT4, HTTP-сервер. Защитные механизмы на месте: карта невидима рабочим сессиям (`CUDA_VISIBLE_DEVICES` пуст), и только `outils/carte.sh` предоставляет её, под блокировкой, для одного измерения за раз; наблюдатель журналирует любой доступ вне блокировки; измерение энергии, охватывающее более одной карты или менее 10 с, отбрасывается; модель, загруженная в деградированном режиме, объявляет это и не участвует в дуэли.

4 107 тестов (`pytest --collect-only -q`, одна минута на процессоре; тесты GPU выполняются только под `carte.sh`). Учёт работы: `acvram-memoire/` (правила, справочник, дневники, обзор нескольких сотен заметок).
