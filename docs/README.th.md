## สองแนวคิด

สร้างขึ้นสำหรับเครื่องเฉพาะเครื่องหนึ่ง:

| | |
|---|---|
| CPU | Intel Core i9-14900K (8 P-core + 16 E-core) |
| เมนบอร์ด | ASUS ROG Maximus Z790 Dark Hero |
| หน่วยความจำ | DDR5 96 GB |
| GPU 0 | ASUS RTX 5090 Astral LC OC, 32 GB — Blackwell, `sm_120` |
| GPU 1 | ASUS RTX 3080 Ti, 12 GB — Ampere, `sm_86` |
| ระบบ | Ubuntu 26.04 LTS (CUDA 13); การ์ดทั้งสองใบทำงานที่ PCIe x8/x8 จำกัดกำลังไฟไว้ที่ 400 W / 275 W |

**หนึ่งรูปแบบต่อหนึ่ง GPU** RTX 5090 มี tensor core สำหรับ FP4 ส่วน RTX 3080 Ti ไม่มีทั้ง tensor core ชนิดนั้นและ FP8 การบังคับให้ทั้งสองใบใช้รูปแบบร่วมกันจะทำให้ศักยภาพของ 5090 สูญเปล่า ตัวแปลงจึงเขียน*โมเดลเดียวกันสองครั้ง* ในรูปแบบที่ปลายทางแต่ละแห่งใช้ประโยชน์ได้จริง:

| | RTX 5090 | RTX 3080 Ti |
|---|---|---|
| น้ำหนัก (weights) | **NVFP4** — E2M1 + สเกล FP8 E4M3 ทุก 16 ค่า | **INT4** — uint4 + สเกลและจุดศูนย์ fp16 ทุก 128 ค่า |
| บิตต่อน้ำหนัก | 4.50 | 4.16 |
| เทียบกับ BF16 | เล็กกว่า ×3.56 | เล็กกว่า ×3.85 |
| โหมดการคำนวณ | tensor core FP4 | dequantize เป็น FP16 ภายในเคอร์เนล แล้วใช้ tensor core FP16 |
| แคช KV | INT8 | INT8 |

VRAM 32 GB ที่ 4.5 บิตต่อน้ำหนักจุพารามิเตอร์ได้ราว **56 พันล้านตัว** เทียบกับ 16 พันล้านตัวใน BF16 เมื่อรวมการ์ดทั้งสองใบ จะได้ประมาณ **78 พันล้านพารามิเตอร์ที่อยู่ในหน่วยความจำ GPU** ก่อนจะต้องแตะหน่วยความจำของโฮสต์เลย

**หน่วยความจำเป็นลำดับชั้น ไม่ใช่กำแพง** มีสามชั้น และตัววางแผน (planner) จะวัดว่าแต่ละชั้นมีต้นทุนจริงเท่าไร แทนที่จะหวังว่าโมเดลจะใส่ได้พอดี:

```
RTX 5090     32 GB   ~1790 GB/s     NVFP4
RTX 3080 Ti  12 GB    ~912 GB/s     INT4
DDR5 โฮสต์    96 GB   ถูกจำกัดโดย PCIe หรือ DDR
```

## เริ่มต้นอย่างรวดเร็ว

```bash
./install.sh                       # สภาพแวดล้อมเสมือน + torch cu128 + acvram
acvram doctor                      # เครื่องนี้พร้อมหรือยัง และพร้อมสำหรับอะไร
acvram detect                      # มีอะไรอยู่ในเครื่องนี้จริง ๆ

acvram plan  ~/models/Qwen3-32B                     # แต่ละเลเยอร์จะถูกวางไว้ที่ใด
acvram convert ~/models/Qwen3-32B -o ~/acv/qwen3-32b
acvram serve ~/acv/qwen3-32b --port 8000
```

ไคลเอนต์ OpenAI ใด ๆ ก็เชื่อมต่อได้ทันที:

```bash
curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3-32b","messages":[{"role":"user","content":"สวัสดี"}],"stream":true}'
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="ไม่ได้ใช้")
client.chat.completions.create(model="qwen3-32b",
                               messages=[{"role": "user", "content": "สวัสดี"}])
```

## ติดตั้ง

จากซอร์สโค้ด (ทุกแพลตฟอร์ม):

```bash
git clone https://github.com/anticitoyun/anticitoyen-vram.git && cd anticitoyen-vram
./install.sh
```

หรือติดตั้งผ่านแพ็กเกจ ซึ่งมีไฟล์แนบมากับทุก [รีลีสบน GitHub](https://github.com/anticitoyun/anticitoyen-vram/releases/latest):

| ช่องทาง | ไฟล์ที่แนบมากับรีลีส | คำสั่ง |
|---|---|---|
| Debian / Ubuntu (.deb) | `acvram_<version>_amd64.deb` | `sudo dpkg -i acvram_<version>_amd64.deb` |
| Arch (AUR) | `aur-<version>.tar.gz` (PKGBUILD + .SRCINFO) | `tar xzf aur-<version>.tar.gz && cd acvram && makepkg -si` |
| Fedora / COPR (RPM) | `.rpm` / `.src.rpm` (ชื่อไฟล์สร้างโดย `rpmbuild` จึงไม่ตายตัว) | `sudo rpm -i acvram-<version>-1.*.noarch.rpm` (หรือ `rpmbuild --rebuild *.src.rpm` จากไฟล์ `.src.rpm`) |
| Flatpak | `acvram-<version>.flatpakref` | `flatpak install --user https://github.com/anticitoyun/anticitoyen-vram/releases/download/v<version>/acvram-<version>.flatpakref` |

ไฟล์ `.flatpakref` จะติดตั้งเวอร์ชันล่าสุดที่เผยแพร่ของที่เก็บข้อมูลเสมอ

ก่อนติดตั้ง ให้ตรวจสอบไฟล์ที่ดาวน์โหลดเทียบกับผลรวมที่แนบมากับรีลีส (`SHA256SUMS` เผยแพร่หลังจากไฟล์อื่นทั้งหมดมีอยู่แล้ว):

```bash
curl -LO https://github.com/anticitoyun/anticitoyen-vram/releases/latest/download/SHA256SUMS
sha256sum -c SHA256SUMS --ignore-missing
```

Pip ไม่ได้เผยแพร่เป็นแพ็กเกจ (ไม่มีการสร้างไฟล์ wheel): `pip install -e '.[dev]'` จะติดตั้งจากซอร์สโค้ดที่โคลนมา เช่นเดียวกับ `./install.sh`

## สิ่งที่ `acvram plan` บอก

ตัววางแผนควรถูกเรียกใช้ก่อนดาวน์โหลดสิ่งใดทั้งสิ้น เพราะมันตอบคำถามที่ตัดสินว่าโมเดลหนึ่งจะใช้งานบนเครื่องนี้ได้หรือไม่:

```
$ acvram plan ~/models/Llama-3.3-70B --max-model-len 32768 --max-seqs 4

  ชั้น     รูปแบบ      ความจุ        น้ำหนัก        KV  ส่วนที่รับ
  cuda:0  nvfp4        30.3 GiB    25.5 GiB   4.5 GiB  เลเยอร์ 0-58
  cuda:1  int4_awq     10.9 GiB     8.7 GiB   1.6 GiB  เลเยอร์ 59-79
  cpu     nvfp4        74.8 GiB     3.4 GiB      0 B   -

  น้ำหนักรวม          37.6 GiB
  อ่านต่อโทเค็น        35.1 GiB
  KV ต่อโทเค็น        162.5 KiB  -> แคชได้ 39,843 โทเค็น
  MLP บน RAM โฮสต์    55-58

  ประมาณการ decode    17.8 โทเค็น/วินาที  (batch ขนาด 1)
  ประมาณการ prefill   847 โทเค็น/วินาที
```

มันสำรวจพื้นที่ของการกำหนดค่าทั้งหมด แทนที่จะหยุดที่การกำหนดค่าแรกที่ใส่ได้ และมีการตัดสินใจสองข้อที่ขัดกับสัญชาตญาณมากพอจะต้องอธิบายให้ชัด:

* **มันปล่อยให้ 3080 Ti ว่างไว้** เมื่อโมเดลใส่บน 5090 ใบเดียวได้ ขั้นตอนต่าง ๆ ของ pipeline ทำงานต่อกันเป็นลำดับ การเพิ่มขั้นตอนที่ 912 GB/s เข้าไปใน pipeline ที่ 1790 GB/s จะทำให้การ decode แบบสตรีมเดียวช้าลง บังคับใช้ได้ด้วย `--gpus all`
* **มันลดขนาดแคช KV เพื่อเก็บน้ำหนักไว้ใน VRAM** ทุกกิกะไบต์ที่ให้แคชคือน้ำหนักหนึ่งกิกะไบต์ที่ถูกผลักไปอยู่บนบัส PCIe และการอ่านน้ำหนักผ่าน PCIe มีต้นทุนราวสามสิบเท่าของการอ่านจาก VRAM สำหรับโมเดล 70B ข้างต้น การแลกเปลี่ยนเพียงข้อนี้ข้อเดียวทำให้ความเร็ว decode เพิ่มจาก 2.3 เป็น 17.8 โทเค็น/วินาที

## ทำให้เร็ว

การปรับให้เหมาะสมสี่อย่าง แต่ละอย่างได้รับการยืนยันด้วยการพิสูจน์ความสมมูล ไม่ใช่แค่การจับเวลา: การปรับให้เหมาะสมที่เปลี่ยนคำตอบคือบั๊ก

เลเยอร์เชิงเส้น NVFP4 ของโมเดลแบบ dense ใช้เลย์เอาต์ Marlin เป็นค่าเริ่มต้น (throughput เพิ่ม +57 ถึง +90% ที่ b = 8, TTFT เพิ่ม +2 ถึง +4 ms ตาม revue/poste6-piece147-verdict-24-09.md; ทางถอยกลับคือ `ACVRAM_PROJ_MARLIN=0` ดู [CHANGELOG.md](../CHANGELOG.md))

### การถอดรหัสแบบคาดเดา (`--speculative`)

การ decode หนึ่งโทเค็นด้วย batch ขนาด 1 ถูกจำกัดด้วยหน่วยความจำ: เครื่องต้องอ่านน้ำหนักที่ใช้งานอยู่ทั้งหมดเพื่อสร้างโทเค็นเพียงตัวเดียว การตรวจสอบโทเค็นที่เสนอมา K ตัวจะอ่านน้ำหนักชุดเดียวกันนั้น**เพียงครั้งเดียว** มีตัวเสนอสองแบบ:

* `ngram` (ค่าเริ่มต้น) — ค้นหาส่วนท้ายปัจจุบันในตำแหน่งก่อนหน้าของบริบท แล้วเสนอสิ่งที่ตามมาหลังจากนั้น ไม่มีต้นทุน ไม่ต้องใช้โมเดล คุ้มค่าเมื่อผลลัพธ์สะท้อนอินพุต: การแก้ไขโค้ด, RAG, การสรุปความ
* `draft` — โมเดลขนาดเล็กบนอุปกรณ์ตัวที่สอง บนเครื่องชุดนี้อุปกรณ์นั้นคือ RTX 3080 Ti ซึ่งตัววางแผนจงใจปล่อยว่างไว้สำหรับโมเดลใดก็ตามที่ใส่บน 5090 ได้

`mtp` (หัว `nextn` ของโมเดล) และ `auto` ก็มีเช่นกัน แต่ในสภาพปัจจุบันยังไม่คุ้มค่าและไม่ได้เปิดใช้เป็นค่าเริ่มต้น — ดู `docs/ARCHITECTURE.md`

การยอมรับเป็นแบบแม่นตรง ไม่ใช่แบบประมาณ: ข้อเสนอจะถูกยอมรับด้วยความน่าจะเป็น `min(1, p/q)` และเมื่อถูกปฏิเสธจะสุ่มใหม่จากส่วนบวกที่ทำให้เป็นมาตรฐานแล้วของ `p - q` เมื่อวัดจากการสุ่ม 40,000 ครั้งเทียบกับโมเดล draft ที่จงใจปรับเทียบผิด การแจกแจงที่ปล่อยออกมายังอยู่ห่างจากเป้าหมายไม่เกิน 0.002 ในระยะ total variation — การคาดเดาซื้อความเร็ว ไม่เคยซื้อคำตอบที่ต่างออกไป

```
โมเดลจำลอง, greedy, k=4        ขั้น   โทเค็น/ขั้น   ผลลัพธ์
  ไม่ใช้การคาดเดา                  23          1.00   ค่าอ้างอิง
  n-gram                         13          1.77   เหมือนกันทุกประการ
  draft (= เป้าหมาย)               5          4.60   เหมือนกันทุกประการ
```

### แคชพรีฟิกซ์ (เปิดเป็นค่าเริ่มต้น)

บล็อกถูกอ้างอิงด้วยแฮช*แบบลูกโซ่*ของช่วงโทเค็นในบล็อกนั้น: คำขอสองรายการที่ใช้ system prompt เดียวกันจะใช้บล็อกของมันร่วมกัน และคำขอที่สองไม่ต้องคำนวณบล็อกเหล่านั้นล่วงหน้าอีก การทำเป็นลูกโซ่เป็นสิ่งจำเป็น: โทเค็นสิบหกตัวเดียวกันในบริบทที่ต่างกันไม่ได้มีคีย์และค่าเหมือนกัน และการแฮชเพียงช่วงโทเค็นนั้นอย่างเดียวจะทำให้แคชของลำดับหนึ่งถูกส่งไปให้อีกลำดับหนึ่ง

บล็อกที่ถูกปล่อยแล้วแต่เนื้อหายังระบุตัวตนได้จะเข้าคิว LRU แทนที่จะกลับไปอยู่ในรายการบล็อกว่าง: ด้วยวิธีนี้แคชจึงอยู่รอดข้ามคำขอได้ โดยไม่เคยปฏิเสธการจัดสรรที่มันสามารถให้บริการได้

### การคำนวณในชั้นโฮสต์ (`--host-exec`)

เลเยอร์ที่น้ำหนักอยู่ใน RAM สามารถถูกคัดลอกไปยัง GPU หรือคำนวณในที่ก็ได้ ทั้งสองทางถูกจำกัดด้วยหน่วยความจำและอ่านไบต์ชุดเดียวกัน: ทางที่เร็วกว่าคือทางที่บัสกว้างกว่า — PCIe 5.0 x16 ให้ราว 54 GB/s ส่วน DDR5 แบบสองแชนเนลให้ราว 70 GB/s — และการคำนวณในที่ยังช่วยให้ GPU ว่างทำงานอื่น แทนที่จะต้องรอการคัดลอก

วิธีนี้คุ้มค่าก็ต่อเมื่อ CPU อ่านน้ำหนัก 4 บิตที่บีบอัดไว้ได้โดยตรง จึงมีเคอร์เนล C++ ขนาดเล็กพร้อมเส้นทาง AVX2 (`acvram_cpu.cpp` โหลดผ่าน ctypes ไม่ต้องใช้ header ของ Python หรือ ninja) แม้แต่บนสาขาสำรองแบบ**สเกลาร์** มันก็ยังเร็วกว่า `dequantize() @ x` 1.44 เท่าใน INT4 และ 3.21 เท่าใน NVFP4 เพราะวิธีหลังต้องเขียนสำเนา 32 บิตของเมทริกซ์ทั้งหมดก่อน

สำหรับ Mistral-Large-123B ค่าประมาณของตัววางแผนเพิ่มจาก 1.35 เป็น 2.42 โทเค็น/วินาที

### ความแม่นยำแบบผสม (`--snr-floor` ปิดเป็นค่าเริ่มต้น)

ตัวแปลงวัดอัตราส่วนสัญญาณต่อสัญญาณรบกวนที่เอาต์พุตของเลเยอร์สำหรับเทนเซอร์ทุกตัว และสามารถยกระดับเทนเซอร์ที่ต่ำกว่า `--snr-floor` ไปเป็นรูปแบบที่กว้างกว่าได้ ภายในเพดาน 15% ของเทนเซอร์ทั้งหมดและเพดานราคา (`--promotion-cout-max` หน่วยเป็นเมบิไบต์ที่เพิ่มขึ้น)

ค่าพื้นเป็น**ศูนย์โดยค่าเริ่มต้น**: ไม่มีสิ่งใดถูกยกระดับ การ decode ถูกจำกัดด้วยแบนด์วิดท์หน่วยความจำ และผลการวัดบน `Huihui-Qwen3.8-27B` เป็นข้อยุติ — ค่าพื้น 25 dB มีต้นทุนหน่วยความจำ 13.4% และ throughput 10.6% (18.50 GiB และ 41.8 t/s เทียบกับ 16.02 และ 46.2) แลกกับ perplexity ที่ดีขึ้น 2.0% (42.591 เทียบกับ 43.447 บนคลังข้อความ 16,383 โทเค็น) `--snr-floor 25` จะคืนพฤติกรรมเดิมเมื่อคุณภาพสำคัญกว่าความเร็ว

### และ `acvram eval`

อัตราส่วนสัญญาณต่อสัญญาณรบกวนและ cosine similarity ของ logit เป็นเพียงค่าประมาณ `acvram eval REP [REP ...]` วัด perplexity แบบหน้าต่างเลื่อน เพื่อให้การเลือกรูปแบบตัดสินกันด้วยหลักฐาน:

```
$ acvram eval ~/acv/qwen3-32b-nvfp4 ~/acv/qwen3-32b-int4
  โมเดล                    ppl     bpp        ขนาด     โทเค็น
  qwen3-32b-nvfp4        6.412    4.51     17.4 GiB      8192
  qwen3-32b-int4         6.583    4.17     16.1 GiB      8192  (+2.7%)
```

<a id="chiffres"></a>

## ตัวเลขมาจากไหน

ค่าทุกค่าที่อ้างถึงข้างต้นมาจากโค้ดในรีโพสิทอรีนี้ และถูกตรวจสอบด้วย `pytest` ผลการวัดบน CPU ด้วยเคอร์เนลอ้างอิง:

| รูปแบบ | บิต/น้ำหนัก | SNR ของน้ำหนัก | cosine ของ logit เทียบ BF16 |
|---|---|---|---|
| BF16 | 16.00 | — | 1.0000 |
| INT8 | 8.19 | 44.6 dB | 0.9998 |
| NVFP4 | 4.50 | 20.4 dB | 0.9664 |
| INT4 | 4.16 | 20.0 dB | 0.9427 |
| INT4 + Hadamard | 4.16 | 21.0 dB | 0.9582 |

ข้อค้นพบสองข้อจากการวัดเหล่านี้ทำให้ค่าเริ่มต้นเปลี่ยนไป:

* **การหมุน Hadamard ช่วย INT4 แต่ไม่ช่วย NVFP4** กลุ่มขนาด 128 ของ INT4 ไม่สามารถดูดซับแชนเนลค่าผิดปกติที่โดดเดี่ยวได้ การกระจายค่าสุดขั้วออกไปจึงคุ้มกับการแปลงขนาด n log n ต่อ activation ส่วนบล็อกขนาด 16 ของ NVFP4 มีสเกลของตัวเองอยู่แล้ว จึงเป็นที่มาของ `--hadamard auto` ซึ่งใช้การหมุนนี้กับ INT4 เท่านั้น
* **INT8 ชนะ FP8 E4M3 สำหรับแคช KV** ที่ 44 dB เทียบกับ 32 dB ในขนาดเท่ากัน เพราะสเกลต่อ (โทเค็น, head) ให้ช่วงไดนามิกที่ FP8 ต้องใช้บิตเลขชี้กำลังแลกมาอยู่แล้ว การ์ดทั้งสองใบจึงใช้แคช KV แบบ INT8 แม้ว่า 5090 จะทำ FP8 ได้ก็ตาม รูปแบบ `k8v4` (ค่าเป็น INT4 ลดไบต์ของแคช −22%) มีให้เป็นตัวเลือก แต่**ยังไม่ผ่านการรับรอง** — ดู `docs/ARCHITECTURE.md`

ในเช้าวันที่ 2026-09-14 acvram อยู่ที่ 630 t/s และ 0.619 J/โทเค็น บนเซลล์เดียวกัน: ผลที่ดีขึ้นมาจาก MMA แบบ FP4 เนทีฟของ Blackwell (`mma.sync … kind::mxf4nvf4` ×7.9 เมื่อเทียบกับ bf16), MoE แบบ grouped-GEMM ต่อกลุ่มขนาด batch, การ routing ด้วยเคอร์เนลเดียว (3,677 → 1,517 การเรียกเคอร์เนลต่อขั้น) และ GEMM แบบแคบบน tensor core สำหรับ projection ตัวเลขทุกตัวมีบันทึกของตัวเองใน `acvram-memoire/revue/` พร้อมคำทำนายที่ผนึกไว้ก่อนการวัด เครื่องมือวัด และสภาวะการวัด — ตัวเลขที่ไม่มีสภาวะการวัดจะไม่ถูกเผยแพร่

จุดที่ acvram นำ: โมเดล MLA (GLM-4.7-Flash) ใน NVFP4 เนทีฟบน sm_120 ซึ่ง vLLM ให้บริการได้เพียงใน FP8 (b=1: 165.35 t/s ในการให้บริการจริง) และโมเดลที่ใส่ใน VRAM ไม่ได้ การ decode แบบลำดับเดียวไม่ได้อยู่ในกลุ่มนี้: เมื่อไม่ใช้การคาดเดา acvram นำ vLLM อยู่ 9.7% (หมายเหตุ ³) ตามหลัง llama.cpp 5.8% ด้าน throughput แต่นำ 13.4% ด้านพลังงาน (หมายเหตุ ⁴) ที่ batch ขนาดใหญ่บนโมเดล MoE ที่ใส่ใน VRAM ได้ vLLM มี throughput เท่ากันที่ b=12 (1,995.1 เทียบกับ 2,027.0 t/s ต่ำกว่า 2σ หมายเหตุ ²) แต่ยังได้เปรียบด้าน J/โทเค็น 7.0% ส่วน acvram พัฒนาขึ้นจาก 1,540 t/s (0.6.34) เป็น 1,995 (0.6.38)

## สถานะ

เวอร์ชัน 0.6.38 ทุกอย่างทำงานบน 5090: เคอร์เนล CUDA คอมไพล์สำหรับ `sm_120a` (FP4 เนทีฟ) และ `sm_86`, CUDA graph, การ quantize แบบ NVFP4/INT8/INT4, เซิร์ฟเวอร์ HTTP มีกลไกป้องกันดังนี้: การ์ดมองไม่เห็นจากเซสชันทำงาน (`CUDA_VISIBLE_DEVICES` ว่าง) และมีเพียง `outils/carte.sh` ที่ให้ยืมการ์ดภายใต้การล็อก ครั้งละหนึ่งการวัด มีตัวเฝ้าระวังบันทึกการเข้าถึงใด ๆ ที่อยู่นอกการล็อก การวัดพลังงานที่ครอบคลุมการ์ดมากกว่าหนึ่งใบหรือสั้นกว่า 10 s จะถือเป็นโมฆะ และโมเดลที่ถูกโหลดในสภาวะลดทอนประสิทธิภาพจะแจ้งเช่นนั้นและไม่เข้าร่วมการประลอง

4,107 เทสต์ (`pytest --collect-only -q` ใช้เวลาหนึ่งนาทีบน CPU; เทสต์ GPU รันได้เฉพาะภายใต้ `carte.sh`) บันทึกการทำงาน: `acvram-memoire/` (กฎ ทำเนียบ สมุดบันทึก และบันทึกการตรวจทานหลายร้อยฉบับ)
