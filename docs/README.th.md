เกตเวย์อนุมานที่เข้ากันได้กับ API ของ OpenAI ซึ่งมองหน่วยความจำเป็นลำดับชั้น
และมอบรูปแบบตัวเลขที่ซิลิคอนของแต่ละ GPU อ่านได้ดีที่สุดให้แก่ GPU นั้น

ออกแบบมาสำหรับเครื่องเฉพาะเครื่องเดียว:

| | |
|---|---|
| โปรเซสเซอร์ | Intel Core i9-14900K (8 คอร์ P + 16 คอร์ E) |
| เมนบอร์ด | ASUS ROG Maximus Z790 Dark Hero |
| หน่วยความจำ | 96 GB DDR5 |
| GPU 0 | ASUS RTX 5090 Astral LC OC, 32 GB — Blackwell, `sm_120` |
| GPU 1 | ASUS RTX 3080 Ti, 12 GB — Ampere, `sm_86` |
| ระบบ | Ubuntu 26.04 LTS (CUDA 13); การ์ดทั้งสองใบอยู่บน PCIe x8/x8 จำกัดที่ 400 W / 275 W |

## แนวคิดสองข้อ

**หนึ่งรูปแบบต่อหนึ่ง GPU** RTX 5090 มีเทนเซอร์คอร์ FP4 ส่วน RTX 3080 Ti ไม่มี
และไม่มี FP8 ด้วย การจับทั้งคู่ให้ใช้รูปแบบร่วมกันจะทำให้ 5090 เสียเปล่า
ตัวแปลงจึงเขียน *โมเดลเดียวกันสองครั้ง* ในรูปแบบที่ปลายทางแต่ละแห่งใช้ประโยชน์ได้จริง:

| | RTX 5090 | RTX 3080 Ti |
|---|---|---|
| น้ำหนัก | **NVFP4** — E2M1 + สเกล FP8 E4M3 ทุก 16 | **INT4** — uint4 + สเกลและศูนย์ fp16 ทุก 128 |
| บิตต่อน้ำหนัก | 4,50 | 4,16 |
| เทียบกับ BF16 | เล็กกว่า ×3,56 | เล็กกว่า ×3,85 |
| โหมดคำนวณ | เทนเซอร์คอร์ FP4 | ถอดควอนไทซ์เป็น FP16 ในเคอร์เนล, เทนเซอร์คอร์ FP16 |
| แคช KV | INT8 | INT8 |

VRAM 32 GB ที่ 4,5 บิตต่อน้ำหนักบรรจุพารามิเตอร์ได้ประมาณ **56 พันล้าน** เทียบกับ
16 พันล้านใน BF16 บนการ์ดสองใบรวมกันคือประมาณ **78 พันล้านพารามิเตอร์ที่อยู่ประจำ**
ก่อนจะแตะ RAM เสียอีก

**หน่วยความจำคือลำดับชั้น ไม่ใช่กำแพง** สามชั้น และตัววางแผนวัดว่าแต่ละชั้นมีต้นทุนเท่าไร
แทนที่จะหวังว่าโมเดลจะพอดี:

```
RTX 5090     32 Go   ~1790 Go/s     NVFP4
RTX 3080 Ti  12 Go    ~912 Go/s     INT4
DDR5 hôte    96 Go   limité par le PCIe ou la DDR
```

## เริ่มต้นอย่างรวดเร็ว

```bash
./install.sh                       # environnement virtuel + torch cu128 + acvram
acvram doctor                      # cette machine est-elle prête, et pour quoi
acvram detect                      # qu'y a-t-il réellement ici

acvram plan  ~/modeles/Qwen3-32B                    # où irait chaque couche
acvram convert ~/modeles/Qwen3-32B -o ~/acv/qwen3-32b
acvram serve ~/acv/qwen3-32b --port 8000
```

จากนั้นไคลเอนต์ OpenAI ใดก็เชื่อมต่อได้:

```bash
curl http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3-32b","messages":[{"role":"user","content":"Bonjour"}],"stream":true}'
```

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:8000/v1", api_key="inutilise")
client.chat.completions.create(model="qwen3-32b",
                               messages=[{"role": "user", "content": "Bonjour"}])
```

## `acvram plan` บอกอะไร

ตัววางแผนควรถูกรันก่อนการดาวน์โหลดใด ๆ มันตอบคำถามที่ตัดสินว่าโมเดลใช้งานได้บนเครื่องนี้หรือไม่:

```
$ acvram plan ~/modeles/Llama-3.3-70B --max-model-len 32768 --max-seqs 4

  etage   format      capacite      poids         KV  tranche
  cuda:0  nvfp4        30,3 Gio   25,5 Gio   4,5 Gio  couches 0-58
  cuda:1  int4_awq     10,9 Gio    8,7 Gio   1,6 Gio  couches 59-79
  cpu     nvfp4        74,8 Gio    3,4 Gio       0 o  -

  poids au total     37,6 Gio
  lu par jeton       35,1 Gio
  KV par jeton       162,5 Kio  -> 39 843 jetons en cache
  MLP en RAM hote    55-58

  decodage estime    17,8 jetons/s  (lot de 1)
  prefill estime     847 jetons/s
```

มันสำรวจพื้นที่ของการกำหนดค่าแทนที่จะเลือกอันแรกที่พอดี และการตัดสินใจสองข้อของมัน
ขัดกับสัญชาตญาณพอที่จะต้องระบุไว้:

* **มันปล่อย 3080 Ti ไว้ไม่ใช้งาน** เมื่อโมเดลพอดีบน 5090 เพียงใบเดียว ส่วนต่าง ๆ ของ
  ไปป์ไลน์ทำงานเป็นอนุกรม: การเพิ่มขั้น 912 GB/s เข้าไปในไปป์ไลน์ 1790 GB/s
  ทำให้การถอดรหัสแบบสตรีมเดียวช้าลง บังคับได้ด้วย `--gpus all`
* **มันหดแคช KV เพื่อรักษาน้ำหนักไว้ใน VRAM** ทุกกิกะไบต์ที่มอบให้แคชคือน้ำหนัก
  หนึ่งกิกะไบต์ที่ถูกผลักไปบนบัส PCIe และการอ่านน้ำหนักผ่าน PCIe มีต้นทุนราวสามสิบเท่า
  ของการอ่านจาก VRAM บน 70B ข้างต้น การตัดสินใจนี้เพียงอย่างเดียวพาจาก 2,3 ไป
  17,8 โทเค็น/วินาที

## ไปให้เร็ว

การปรับแต่งสี่อย่าง แต่ละอย่างตรวจสอบด้วยการพิสูจน์ความสมมูล ไม่ใช่แค่นาฬิกาจับเวลา:
การปรับแต่งที่เปลี่ยนคำตอบคือบั๊ก

### การถอดรหัสแบบคาดเดา (`--speculative`)

การถอดรหัสหนึ่งโทเค็นด้วยแบตช์ขนาด 1 ถูกจำกัดด้วยหน่วยความจำ: เครื่องอ่านน้ำหนัก
ที่ใช้งานทั้งหมดเพื่อผลิตโทเค็นเพียงตัวเดียว การตรวจสอบโทเค็นที่เสนอ K ตัวอ่านน้ำหนัก
ชุดเดียวกันนั้น **เพียงครั้งเดียว** ผู้เสนอสองแบบ:

* `ngram` (ค่าเริ่มต้น) — ค้นหาส่วนท้ายปัจจุบันในบริบทก่อนหน้าและเสนอสิ่งที่ตามมา
  ไม่มีต้นทุน ไม่ต้องใช้โมเดล คุ้มค่าเมื่อผลลัพธ์คัดลอกอินพุต: แก้ไขโค้ด, RAG, สรุปความ
* `draft` — โมเดลเล็กบนอุปกรณ์ที่สอง บนเครื่องนี้อุปกรณ์นั้นคือ RTX 3080 Ti
  ซึ่งตัววางแผนจงใจปล่อยว่างสำหรับโมเดลใดก็ตามที่พอดีบน 5090

การยอมรับนั้นแม่นยำ ไม่ใช่ประมาณ: ข้อเสนอถูกยอมรับด้วยความน่าจะเป็น `min(1, p/q)`
และการปฏิเสธจะสุ่มใหม่จากส่วนบวกที่ปรับให้เป็นมาตรฐานของ `p - q` วัดจากการสุ่ม
40 000 ครั้งเทียบกับร่างที่จงใจปรับเทียบไม่ดี การแจกแจงที่ปล่อยออกมายังอยู่ภายใน
0,002 ของความแปรผันรวมจากเป้าหมาย — การคาดเดาซื้อความเร็ว ไม่เคยซื้อคำตอบที่ต่างไป

```
modele jouet, glouton, k=4    etapes   jetons/etape   sortie
  sans speculation                23           1,00   reference
  n-grammes                       13           1,77   identique
  brouillon (= cible)              5           4,60   identique
```

### แคชคำนำหน้า (เปิดใช้เป็นค่าเริ่มต้น)

บล็อกถูกระบุตำแหน่งด้วยแฮช *แบบลูกโซ่* ของช่วงโทเค็นของมัน: คำขอสองรายการที่ใช้
คำสั่งระบบร่วมกันจะใช้บล็อกร่วมกัน และรายการที่สองไม่ต้องคำนวณล่วงหน้าอีก การทำ
ลูกโซ่จำเป็นอย่างยิ่ง: โทเค็นสิบหกตัวเดียวกันในบริบทต่างกันไม่ได้มีคีย์และค่าเดียวกัน
และการแฮชเฉพาะช่วงจะเสิร์ฟแคชของลำดับหนึ่งให้อีกลำดับหนึ่ง

บล็อกที่ถูกปล่อยแต่เนื้อหายังระบุได้จะเข้าคิว LRU แทนรายการบล็อกว่าง: แคชจึงอยู่รอด
ระหว่างคำขอโดยไม่เคยปฏิเสธการจัดสรรที่มันเสิร์ฟได้

### การคำนวณที่ชั้นโฮสต์ (`--host-exec`)

เลเยอร์ที่น้ำหนักอยู่ใน RAM สามารถคัดลอกไป GPU หรือคำนวณในที่ได้ ทั้งสองเส้นทางถูก
จำกัดด้วยหน่วยความจำและอ่านไบต์ชุดเดียวกัน: เส้นทางที่เร็วกว่าคือเส้นทางที่บัสกว้างกว่า —
PCIe 5.0 x16 ให้ราว 54 GB/s, DDR5 สองช่องราว 70 GB/s — และการคำนวณในที่ยังปล่อยให้
GPU ว่างแทนที่จะให้มันรอสำเนา

สิ่งนี้คุ้มค่าต่อเมื่อโปรเซสเซอร์อ่านน้ำหนักที่แพ็ก 4 บิตโดยตรง จึงมีเคอร์เนล C++ ขนาดเล็ก
ที่มีเส้นทาง AVX2 (`acvram_cpu.cpp` โหลดผ่าน ctypes ไม่ต้องใช้เฮดเดอร์ Python หรือ ninja)
แม้บนกิ่งสำรอง **แบบสเกลาร์** มันก็ชนะ `dequantize() @ x` 1,44 เท่าใน INT4 และ 3,21 เท่าใน
NVFP4 เพราะอย่างหลังเขียนสำเนา 32 บิตของเมทริกซ์ทั้งหมดก่อน

บน Mistral-Large-123B ค่าประมาณของตัววางแผนเพิ่มจาก 1,35 เป็น 2,42 โทเค็น/วินาที

### ความแม่นยำแบบผสม (`--snr-floor` ปิดเป็นค่าเริ่มต้น)

ตัวแปลงวัดอัตราส่วนสัญญาณต่อสัญญาณรบกวนที่เอาต์พุตของแต่ละเลเยอร์สำหรับแต่ละเทนเซอร์
และสามารถเลื่อนเทนเซอร์ที่ต่ำกว่า `--snr-floor` ไปยังรูปแบบที่กว้างกว่าได้ ภายในขีดจำกัด
15 % ของเทนเซอร์และเพดานราคา (`--promotion-cout-max` เป็นเมบิไบต์ที่เพิ่ม)

ค่าพื้นคือ **ศูนย์เป็นค่าเริ่มต้น**: ไม่มีอะไรถูกเลื่อน การถอดรหัสถูกจำกัดด้วยแบนด์วิดท์
หน่วยความจำ และการวัดบน `Huihui-Qwen3.8-27B` ตัดสิน — ค่าพื้น 25 dB มีต้นทุน 13,4 %
ของหน่วยความจำและ 10,6 % ของทรูพุต (18,50 GiB และ 41,8 t/s เทียบกับ 16,02 และ 46,2)
แลกกับ perplexity 2,0 % (42,591 เทียบกับ 43,447 คลังข้อความ 16 383 โทเค็น)
`--snr-floor 25` คืนพฤติกรรมเดิมเมื่อคุณภาพสำคัญกว่าความเร็ว

### และ `acvram eval`

อัตราส่วนสัญญาณต่อสัญญาณรบกวนและโคไซน์ของ logits เป็นค่าประมาณ
`acvram eval DIR [DIR ...]` วัด perplexity ด้วยหน้าต่างเลื่อน เพื่อให้การเลือกรูปแบบ
ตัดสินด้วยหลักฐาน:

```
$ acvram eval ~/acv/qwen3-32b-nvfp4 ~/acv/qwen3-32b-int4
  modele                   ppl     bpp      taille    jetons
  qwen3-32b-nvfp4        6,412    4,51    17,4 Gio      8192
  qwen3-32b-int4         6,583    4,17    16,1 Gio      8192  (+2,7 %)
```

## จุดเชื่อมต่อ HTTP

| จุดเชื่อมต่อ | หมายเหตุ |
|---|---|
| `POST /v1/chat/completions` | สตรีม SSE หรือคำตอบเดียว; ใช้เทมเพลตการสนทนาของโมเดล |
| `POST /v1/completions` | พรอมต์เป็นข้อความหรือรหัสโทเค็น |
| `POST /v1/embeddings` | สถานะซ่อนสุดท้ายเฉลี่ย ปรับมาตรฐาน L2 เคารพ `dimensions` |
| `GET /v1/models` | พร้อมบล็อก `acvram`: รูปแบบ อุปกรณ์ ความจุแคช KV |
| `GET /health`, `GET /metrics` | ทรูพุตการถอดรหัส การใช้งานบล็อก KV |

ชื่อฟิลด์ในคำตอบเหล่านี้ยังคงเป็นภาษาอังกฤษ: นี่คือโปรโตคอล OpenAI และการแปล
จะทำให้ไคลเอนต์ที่มีอยู่ทั้งหมดพัง

## ตัวเลขมาจากไหน

ทุกค่าที่อ้างข้างต้นผลิตโดยโค้ดในที่เก็บนี้และตรวจสอบโดย `pytest` การวัดทำบน
โปรเซสเซอร์ด้วยเคอร์เนลอ้างอิง:

| รูปแบบ | บิต/น้ำหนัก | SNR ของน้ำหนัก | โคไซน์ของ logits เทียบ BF16 |
|---|---|---|---|
| BF16 | 16,00 | — | 1,0000 |
| INT8 | 8,19 | 44,6 dB | 0,9998 |
| NVFP4 | 4,50 | 20,4 dB | 0,9664 |
| INT4 | 4,16 | 20,0 dB | 0,9427 |
| INT4 + Hadamard | 4,16 | 21,0 dB | 0,9582 |

ข้อค้นพบสองข้อจากการวัดเหล่านี้เปลี่ยนค่าเริ่มต้น:

* **การหมุน Hadamard ช่วย INT4 แต่ไม่ช่วย NVFP4** กลุ่ม 128 ของ INT4 ดูดซับช่องสัญญาณ
  ผิดปกติเดี่ยว ๆ ไม่ได้ การกระจายค่าสุดขั้วจึงคุ้มกับการแปลง n log n ต่อการกระตุ้น
  บล็อก 16 ของ NVFP4 มีสเกลของตัวเองอยู่แล้ว จึงมี `--hadamard auto` ที่ใช้กับ INT4 เท่านั้น
* **INT8 ชนะ FP8 E4M3 สำหรับแคช KV** 44 dB เทียบ 32 dB ที่ขนาดเท่ากัน เพราะสเกลต่อ
  (โทเค็น, หัว) ให้ช่วงไดนามิกที่ FP8 ต้องใช้บิตเลขชี้กำลังไปแลกอยู่แล้ว การ์ดทั้งสอง
  จึงใช้แคช KV แบบ INT8 แม้ 5090 จะทำ FP8 ได้

## ผลที่วัดได้ (22/09/2026, RTX 5090 ที่ 400 W, ระบอบ ≥ 20 วินาทีบนมิเตอร์พลังงาน)

Qwen3-Coder-30B-A3B ใน NVFP4 (ผู้เชี่ยวชาญ) + INT8 (แอตเทนชัน, หัว) โปรโตคอลเดียวกัน
สำหรับทุกเอนจิน (`outils/`, การ์ดเดียว, `energie.py`):

| | acvram 0.6.35 | vLLM 0.29 (CUTLASS FP4) | llama.cpp (sm_120) |
|---|---|---|---|
| ถอดรหัส 12 ลำดับ | **1634 t/s** | 1782 t/s | — |
| ถอดรหัส 1 ลำดับ | **380,8 t/s** | 290,6 t/s | 323,6 t/s |
| prefill pp2048 | **22 707** โทเค็น/วินาที | 21 054 | 8 671 (TabbyAPI, ถอนออก) |

ทรูพุตของวันนี้ (แท่น 1030, ระบอบประหยัด `-lgc 2700`, ไปป์ไลน์ที่ให้บริการ; การสุ่มแบบละโมบถูกจับไว้ในกราฟ CUDA, ค่าเริ่มต้นตั้งแต่ 0.6.35) b=12 เป็นเซลล์ทางการที่ผนึกไว้ (มัธยฐานของ 6 หน้าต่างที่สลับกัน, ความถี่ต่อหน้าต่าง)

> **Erratum (22/09/2026).** การเผยแพร่ครั้งแรกของ 0.6.35 อ้าง «+1,84 % นำหน้า vLLM» จากค่าอ้างอิง vLLM ที่ 1596 t/s ของ 21/09 ซึ่งมาจาก**การสร้างแบบออฟไลน์** (`LLM().generate()`) **ที่เทียบกับเซิร์ฟเวอร์ไม่ได้**: ไม่มีการจัดตารางต่อเนื่อง ไม่ใช่เส้นทางของ `acvram serve` แก้ไขเมื่อ 22/09 ด้วยเซลล์สลับ A/V (A1 V1 A2 V2 A3 V3) เทียบกับ **`vllm serve`** (HTTP) การ์ดเดียวกันและเส้นทางเดียวกับ `acvram serve`: มัธยฐาน vLLM **1782 t/s** ที่การวัดเทียบเคียงได้ **acvram (1634 t/s) ตามหลัง vLLM ราว 8 % ที่ b=12** ไม่ใช่นำหน้า ค่า J/โทเค็นที่ความถี่เท่ากันยังต้องวัดใหม่

เช้าวันที่ 14/09 acvram อยู่ที่ 630 t/s และ 0,619 J/โทเค็นบนเซลล์เดียวกัน: กำไรมาจาก
MMA FP4 แบบเนทีฟของ Blackwell (`mma.sync … kind::mxf4nvf4`, ×7,9 เหนือ bf16), จาก MoE
เป็น GEMM แบบจัดกลุ่มต่อถังแบตช์, จากการกำหนดเส้นทางในเคอร์เนลเดียว (3 677 → 1 517
การเรียกต่อขั้น) และจาก GEMM แคบบนเทนเซอร์คอร์สำหรับการฉาย ทุกตัวเลขมีบันทึกของมันใน
`acvram-memoire/revue/` พร้อมการทำนายที่ผนึกไว้ก่อนวัด เครื่องมือ และระบอบของมัน —
ตัวเลขที่ไม่มีระบอบจะไม่ถูกเผยแพร่

ที่ acvram นำหน้า: โมเดล MLA (GLM-4.7-Flash) ใน NVFP4 เนทีฟ sm_120 ซึ่ง vLLM เสิร์ฟได้เฉพาะ FP8 (b=1: 165,35 t/s ที่ให้บริการ); โมเดลที่ไม่พอดี VRAM; และการถอดรหัสลำดับเดียว (b=1: 380,8 t/s เทียบกับ 290,6 ของ vLLM) ในทางกลับกัน ที่แบตช์ใหญ่ บน MoE ที่พอดี VRAM vLLM ยังคงนำหน้าที่ b=12 (1782 เทียบกับ 1634 t/s ดู erratum); acvram พัฒนาขึ้น (1540 ใน 0.6.34 → 1634) แต่ไม่แซงหน้า ส่วนต่างด้านพลังงานยังต้องวัดใหม่

## สถานะ

เวอร์ชัน 0.6.35 ทุกอย่างทำงานบน 5090: เคอร์เนล CUDA คอมไพล์สำหรับ `sm_120a` (FP4 เนทีฟ)
และ `sm_86`, กราฟ CUDA, ควอนไทเซชัน NVFP4/INT8/INT4, เซิร์ฟเวอร์ HTTP ราวกันตกอยู่ครบ:
การ์ดมองไม่เห็นจากเซสชันทำงาน (`CUDA_VISIBLE_DEVICES` ว่าง) และมีเพียง `outils/carte.sh`
ที่ให้ยืมภายใต้ล็อกแก่การวัดทีละหนึ่ง; ยามบันทึกทุกการเข้าถึงนอกล็อก; การวัดพลังงานที่
ครอบคลุมมากกว่าหนึ่งการ์ดหรือสั้นกว่า 10 วินาทีถือเป็นโมฆะ; โมเดลที่โหลดในระบอบเสื่อม
จะบอกเช่นนั้นและไม่เข้าประลอง

การทดสอบ 640 รายการ (`pytest -q` หนึ่งนาทีบนโปรเซสเซอร์; การทดสอบ GPU รันเฉพาะภายใต้
`carte.sh`) การติดตามงาน: `acvram-memoire/` (กฎ ทำเนียบ สมุดบันทึก การทบทวน 180 บันทึก)
