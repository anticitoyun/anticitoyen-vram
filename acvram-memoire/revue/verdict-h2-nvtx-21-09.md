verdict : **RÉFUTÉ comme posé — cause structurelle, pas un bogue de la range.** `eng.step()` sous graphe appelle `GraphRunner.rejouer_suivant` (`graphs.py:580`) : un seul `cudaGraphLaunch` opaque qui rejoue les nœuds capturés — le code Python de `decode_fixed`/`MoEBlock.forward` (où vivent mes `nvtx.range_push`) **ne s'exécute plus une fois le graphe capturé** ; mes ranges n'ont tourné que pendant `warm_graphs()`, AVANT `cudaProfilerStart` — `--capture-range=cudaProfilerApi` jette tout ce qui est hors fenêtre, d'où 0 ligne. Aucun NVTX posé au niveau Python ne peut donc jamais attribuer un noyau des 50 pas mesurés en régime servi (graphes on) — la seule fenêtre où le graphe n'est pas encore capturé (`CERT_EAGER=1` ou avant `warm_graphs`) mesurerait un régime jamais servi (REGLES § 3 : « une occupation prédite se vérifie dans le régime du moteur, jamais à un autre régime »).
