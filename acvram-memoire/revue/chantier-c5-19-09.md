# Chantier C5 — cache KV int8 au décodage : régime établi, arrondi borné à sec (19/09, branche `oceane-c5-kv-int8`)

**Objectif** (sage-poursuite-chantiers-19-09 § 2, C5) : `kvcache._dequantize` existe — établir le régime, le mesurer, le mettre au défaut si tenu. Aucune mesure carte ce soir ; tout à sec.

**Prédiction scellée** (décision Sage, sage-c2-c4-c5-tranches-19-09 : une grandeur, un seuil) : **`ppl-decode-kv` int8 contre bf16 sur le converti servi, ΔPPL = PPL_int8 − PPL_bf16 ≤ +0,004** ; sinon faux. Issue qui me gênerait : ΔPPL > +0,004 — alors int8, DÉJÀ le défaut, coûte de la qualité à chaque mesure publiée depuis le 15/09. Les deux autres lignes de la commande (« ms/pas b=12 ctx 4 k ≤ 1,00 × bf16 », « séquences concurrentes × 2 à VRAM égale ») sont des **résultats publiés**, pas des scellés : la première compare deux chemins d'attention (ci-dessous), la seconde est bornée à × 1,969 par construction (table VRAM).

## Ce qui existe déjà (lecture du code, fichier:ligne)
* **int8 existe et EST le défaut effectif.** `kvcache.py:241` (`dtype: str = "int8"`) ; `_quantize` `kvcache.py:362-375` : échelle fp16 par (jeton, tête) = amax/127, code `round(x/échelle)` borné ±127 — pas par bloc ; `_dequantize` `kvcache.py:377-384` ; octets par bloc `kvcache.py:269-274`. Chemin CUDA fusionné `kv_write_int8` `kvcache.py:412-424` (bf16 sur carte seulement).
* **Qui décide du format** : `tiering.py:48-50` lit `ACVRAM_KV_FORMAT` à l'import (`_KV_FORMAT`) ; `tiering.py:367` `kvf = _KV_FORMAT or caps.kv_format` ; `loader.py:190-196` `_kv_format` (variable sinon palier du plan, sinon int8) ; `detect.py:123-133` : int8 pour fp4 (5090), fp8, bf16 (3080 Ti), fp16 seulement avant Ampere ; palier hôte fp16 `tiering.py:398`.
* **Régime** : `ACVRAM_KV_FORMAT` vide → **int8** (le défaut effectif sur Coder, ce que `ppl-decode-kv-17-09.py:41` imprime en `kv_dtype_effectif`) ; `=bf16` → bf16, `=int8` → int8 explicite ; `fp16`, `fp8_e4m3`, `lm4/lm3/lm2` acceptés (`tiering.py:49`). **GLM : la variable ne s'applique à rien** — MLA (`kv_lora_rank` 512, `config.py:263-283` `couche_a_kv` faux), aucun cache paginé, latent bf16 (`mla.py:44,356`, `ACVRAM_MLA_LATENT_FP8=0`) ; verdict-kv-int8-glm-17-09 le disait déjà. C5 ne concerne que les modèles à KV paginé (Coder, Nemotron, Qwen3-Next…).
* **Le bras bf16 change de chemin d'attention** : `kernels/__init__.py:1179-1180` refuse le noyau paginé hors int8 → `model.py:455-461` repli `gather_fixed` + `decode_attention_fixed` (torch, tout le contexte relu et déquantifié à chaque pas). Le 17/09 (verdict-kv-lm4-qualite, Laure) : int8/bf16 = 0,998 « au seuil, chemins différents », capacité 1,97×. « ≤ 1,00 × bf16 » en ms/pas compare donc noyau paginé contre repli torch, pas deux formats sur le même noyau — un « tenu » facile qui ne dit rien du format ; le chiffre qui vaut est le ms/pas int8 absolu à b=12 ctx 4 k.
* **`regime_ligne()` ne portait pas le format KV** quand rien n'était posé : `regime.py:224` n'écrit que `hors_defaut` (vide = rien), `runner.py:615-631` ne le lisait pas du tout. Toutes les lignes de régime publiées depuis le 15/09 ont mesuré int8 sans l'écrire.

## État
* **Fait** : régime établi et nommé dans les deux lignes ; arrondi borné et dit, témoins cassants ; puits : chemin commun ; table VRAM.
* **Reste** (carte) : la PPL et le ms/pas ci-dessous ; décision « défaut » : int8 l'est déjà — un « tenu » ne change rien, un « faux » impose soit bf16 par défaut (moitié des séquences ET perte du noyau paginé) soit un noyau paginé bf16 : à trancher après la mesure, pas avant.
* **Non vérifié** : équivalence des codes `kv_write_int8` (CUDA) ↔ `_quantize` (torch) — sur carte seulement (test_rope_kv en tenait un sur 6 jetons) ; l'attention paginée int8 lit les échelles fp16 comme `_dequantize` (noyau Triton/CUDA, `kernels/__init__.py:1187-1196`) ; le coût réel des canaux ordinaires du puits (22 % à κ=100) sur les logits — c'est la PPL de décodage qui le dit.
